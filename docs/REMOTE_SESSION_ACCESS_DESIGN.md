# Session front door and private remote access (design)

Status: research and evolving design, 2026-11-06. The direct home-Wi-Fi dashboard phase is operational and documented in [Local dashboard access](LOCAL_DASHBOARD_ACCESS.md). Harness session UI and access away from home remain design only. Owning repo: `llm-gateway`. Companion: `llm-harness/docs/REMOTE_SESSIONS_DESIGN.md`.

## Goal and boundary

The Pi gateway presents a small conversation UI and authenticated API for harness sessions. A phone or local browser can attach to a running Pi session while model inference remains on the isolated rig. The gateway handles network reachability, identity, authorization, and event relay. The harness handles the agent's prompts, context, tools, child agents, approvals, and durable session state. The manager handles model readiness and GPU claims. No browser or phone receives a direct rig route.

Current state: `pi-gateway.service` listens on `127.0.0.1:8080`. The existing `/dashboard/` includes powerful rig and orchestration controls and has no API keys yet (`docs/DASHBOARD.md`). A separate HTTPS front door on the Pi's Wi-Fi interface requires a browser client certificate and forwards only dashboard routes at `/gpurig` and `/dashboard/...`. This is home-network operator access, not the proposed harness session surface. A future phone or private VPN listener must not inherit the whole administrative dashboard. Keep rig management and inference administration on loopback unless independently hardened.

## Existing local dashboard and next build

The web UI was already moved from `llm_orchestration` to this repo on 2026-10-20. The Pi gateway now serves one page with Rig, Models, Benchmarks, and Orchestration tabs at `/dashboard/`. Orchestration's status and controls are exposed through its private versioned Unix-socket API; `dashboard/sources.py` calls that API. The existing start form exposes a plan, starter, and raw config JSON. This is the current operator interface, not a new UI migration to schedule.

The next local-only build is a **Work view** that gives the operator one place to start and follow work: a catalog of allowed workflows with typed fields, a durable work/run ID, state and progress events, terminal receipt, artifact links, and a clear failure/retry path. It can first show orchestration batches and manager runs from their existing authoritative sources, then add harness sessions when the harness session service exists. Do not create a second canonical job state in the gateway. Keep the existing administrative Rig controls in their own local-only surface.

The repository boundary now uses versioned orchestration status, options, and action endpoints over a private Unix socket; the gateway no longer imports orchestration code. Orchestration still owns plan definitions, task execution, worker state, and task recovery; the gateway owns presentation and routing. A later notification adapter can consume the same work events. The separate direct LAN dashboard front door does not implement harness sessions or remote access.

Open design questions: which work types belong in the first catalog; how to normalize manager runs, orchestration batches, and harness sessions without hiding their distinct states; which artifacts are safe to preview in the UI; and whether the orchestration contract is a local CLI, a loopback service, or another narrow transport. Decide from a small local prototype and its failure behavior rather than moving the orchestration engine into this repo.

## Traffic and service layout

```text
local browser/phone -- authenticated session UI/API --> Pi gateway session front door
                                                   --> Pi harness session service
                                                       --> Pi gateway inference/roster API
                                                       --> Pi manager child-route API
Pi manager -- private Ethernet/SSH --> rig model runtimes
```

The gateway should proxy session creation, message submission, state, approvals, cancellation, and a resumable event stream. It should not rebuild prompts or persist a second canonical transcript. The gateway may keep a minimal access/audit log with request ID, actor, session ID, action, and outcome, without copying private prompts or tool output. The harness's event sequence is authoritative; the gateway forwards it unchanged. Establish timeouts appropriate to long model turns and streaming so proxy disconnects do not kill sessions.

## Candidate local phases

The administrative dashboard now has a separate, certificate-gated home-LAN front door. The sequence below concerns the future harness **session** UI: core sessions and work contracts first; a Pi-local browser interface next; authenticated home-LAN session access later; access from elsewhere last. Each phase needs a fresh review of earlier evidence. The session security controls below are proposed requirements and test ideas, not evidence that the present dashboard deployment already has them.

1. Keep the inference/manager/dashboard listener at `127.0.0.1:8080`. Run the harness session service on Pi loopback. Add a separate gateway session listener or tightly scoped proxy routes; decide after a threat review of current route/auth behavior.
2. Make a simple UI: list sessions, open transcript, follow progress, send a message, view pending approvals, pause/resume/cancel. A reconnect must replay missed events using the harness's event cursor. Display actual route/model, readiness, running/paused/failed state, and tool/child progress without exposing GPU-control actions.
3. Test through loopback and then the home LAN with an authenticated front door. Do not bind the current unrestricted dashboard to the LAN. Validate origin handling, CSRF protection for browser mutations, secure cookies, session expiry, rate limits, and no credentials in logs.
4. Use existing manager APIs for any explicit `coding` or `research` child preparation. The gateway relays readiness and errors, including 503 no capacity, 504 preparation timeout, and load failure. The harness sends inference with `X-Require-Ready: true` after preparation. Model selection/placement remains a manager policy.

## Private access from elsewhere (later networking milestone)

The desired state is a private route from the operator's phone to the Pi session front door with no public listener on the rig and no router port forward to either host. Tailscale on the phone and Pi, with Tailscale Serve exposing only a loopback session listener to the private tailnet, is the first candidate. Restrict tailnet access policy to the operator's approved devices and the Pi session service. Do not use Tailscale Funnel for this use; it makes the service public. Tailscale device identity is the network gate, not a substitute for the app's authorization and approval checks. A lost phone must be revocable without rotating a shared password across the system.

Reference for the later deployment: [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve), [Funnel](https://tailscale.com/docs/features/tailscale-funnel), and [firewall/port behavior](https://tailscale.com/docs/reference/faq/firewall-ports).

An SSH client/tunnel from the phone is a valid minimal remote option for a technical operator, but an SSH key does not directly authenticate an ordinary mobile browser session. A browser UI needs an authenticated network path plus application identity. A self-managed WireGuard or Headscale deployment and an outbound tunnel with an identity provider are alternatives to compare when the networking milestone starts; they introduce different operating and trust costs. The rig stays off those networks. Explicitly disable IP forwarding from the Pi's remote-access interface to the rig network and check firewall rules; the Pi remains a bridge by application request only, so compromise of the Pi is still material.

## Security requirements and tests

- Threat model: stolen phone, stolen app token, malicious website issuing browser requests, unauthenticated LAN peer, compromised session service, excessive event/log disclosure, and Pi-to-rig privilege expansion. Define which actions the session UI is allowed to invoke. A hidden URL or unusual port is not authentication.
- Separate authorization for read transcript, send message, approve side effects, and cancel work. Initially one operator; preserve distinct action scopes. Require fresh or stronger confirmation for high-impact approvals if tool policy calls for it.
- Bind the harness and management APIs to loopback or Unix sockets. The future remote listener must permit only session UI/API paths. Test direct access to `/dashboard/`, `/v1/manager/`, raw inference, rig tunnels, and the harness backend from the phone/remote path; each should be denied unless specifically authorized by a separate policy. The existing home-LAN dashboard policy is a separate certificate-gated operator exception.
- Protect browser mutations against cross-site requests; use secure, HTTP-only cookies and appropriate origin checks on the remote path. Limit upload and event sizes, concurrent streams, request rate, and idle session duration. Log administrative access and device revocation without logging secrets.
- Test disconnect/reconnect, simultaneous phone and desktop clients, retry after timeout, lost phone revocation, expired login, gateway restart, harness restart, rig outage, manager 503/504, and bounded stream replay. Verify the agent continues or pauses according to harness policy, not the browser TCP connection.
- Before away-from-home use, inspect effective Tailscale ACLs, Serve exposure, router/firewall inbound rules, and Pi forwarding. Use a separate test account/device to prove denied paths. Keep the current dashboard inaccessible over the phone route.

## Open decisions

- Separate listener/process versus path-scoped proxy within the existing gateway: which gives the clearest least-privilege boundary and manageable deployment?
- App authentication: Pi-local passkey/WebAuthn, short-lived session behind tailnet identity, or another approach? Define recovery and revocation without a permanent password shared across devices.
- What identity assertion and transport should the gateway use to the harness? Where are authorization checks enforced to prevent bypass through local services?
- Which event transport works best on mobile networks: server-sent events with cursor replay or WebSocket? Test sleep/wake and network changes before choosing.
- How do UI actions map to manager owner/claims without granting the session front door unrestricted rig control? Define cancellation scope and audit events.
- How long should idle session metadata and attachments remain on Pi storage, and how are they backed up and purged?
- Compare Tailscale with a self-managed option once remote deployment is in scope. Record availability under mobile carrier networks and failure/recovery behavior.

## Channel adapters and Google accounts (proposal, 2026-11-06)

The gateway is the Pi-hosted communications layer for the same harness work/session API. It should accept or deliver messages through a local browser, a later private Tailscale route, Gmail, WhatsApp, and future channels without making any channel the work engine. It authenticates source identity, applies channel-specific policy, turns provider events into a common envelope, and transports harness events back to authorized destinations. A task may be executed by the harness itself, by orchestration, or by another approved executor; the gateway does not force every request into an orchestration plan.

Common inbound envelope: `{channel, account_alias, provider_message_id, thread_id, sender_identity, received_at, text, attachment_refs, idempotency_key}`. The gateway records receipt, rejects unauthenticated/disallowed sources, and forwards a bounded request to the harness. The harness returns a durable work ID and may request clarification. Common outbound request: `{work_id, event_id, destination_role, message_kind, body_or_artifact_ref, idempotency_key}`. The gateway maps destination roles to approved account/address/chat/folder IDs, sends once, and persists provider delivery IDs. The dashboard reads the same work state; it does not own a separate email workflow. Distinguish notifications from inbound command authority.

Google is the first non-browser adapter because a dedicated account and outbound Gmail/Drive helpers already exist. The Pi normally has internet while the rig normally does not, so move OAuth credential custody and Google network calls to a Pi-only connector. Never send tokens to models, candidate controllers, rig plan inputs, shared receipts, or dashboard responses. Give each connected Google account its own alias, scopes, and policy; the automation account stays separate from the primary account. `llm_orchestration/shared/workspace/google.md` documents the existing helper, and the user reports outbound delivery working. Treat it as a prototype to migrate, not a new prerequisite for every harness task.

Initial Gmail intake: poll the dedicated inbox with `gmail.readonly`, preserve message and thread IDs, paginate, and keep a durable processed-message ledger. The existing `read_emails` helper is bounded and omits thread ID, so it is not enough for unattended intake. Gmail push requires Cloud Pub/Sub plus watch renewal; compare only if polling delay becomes a problem. A sender allowlist is a first filter; the accepted actions and approval requirements come from gateway/harness policy. Email text and attachments are untrusted task inputs, never shell commands, tool approvals, or plan definitions. [Gmail list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [push/watch](https://developers.google.com/workspace/gmail/api/guides/push).

Initial outbound: send a short work-started acknowledgment, selected progress/clarification notices, and a terminal result/failure reply in the original thread. Drive delivery uploads only admitted artifacts and returns a file ID/link; the local artifact and receipt remain canonical. An outbox retries delivery without rerunning work. The new connector initially needs `gmail.readonly`, `gmail.send`, and `drive.file`; the old helper's `drive.readonly` is unnecessary for upload-only use. Later Gmail/Drive search tools need separate explicit grants. OAuth refresh-token health and revoked grants appear as connector status without exposing token values. [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [Google OAuth](https://developers.google.com/identity/protocols/oauth2).

The existing orchestration dashboard shows batch starts and completion/failure alerts, and its control path can submit plans. Reuse those signals when orchestration is selected as an executor, but introduce a narrow job adapter rather than giving the email connector the dashboard's broad control API. The earlier dashboard "work starting" idea becomes one event type that can appear in the UI, email, or later WhatsApp. GitHub analysis is one example to test this path; the current full analyzer plan passes an empty URL to `prepare_repo.py` and expects a claimed behavior, so its URL-only/general-analysis mode must be fixed before that example is claimed working. Other test work should include harness-native research, coding, a scheduled report, and a task that needs clarification mid-run.

Acceptance tests: one logical work request arriving twice through Gmail creates one item; a browser can follow that same item; an unauthorized sender creates none; a valid clarification resumes the existing item; a forged reply cannot approve a high-impact action; one harness-native and one orchestration-backed task complete; Drive/email failures retry from outbox; no delivery failure reruns the underlying task; and no credential or full private message leaks into public receipts. Start with mocked providers, then one dedicated-account end-to-end test. A later WhatsApp adapter must pass the same contract tests. Keep the rig isolated throughout.

## Inbound security gates and the Pi-to-rig boundary

Remote access must not reuse the existing gateway dashboard's broad controls as its command API. Currently `llm_orchestration/scripts/dashboard/controls.py` can submit a plan by running `ssh gpu bash -s`; the gateway manager also has privileged rig-management SSH. A Pi process with those credentials can bypass any narrow email parser. Before enabling inbound commands, isolate channel adapters from manager credentials and arbitrary SSH, and replace remote work submission with a small typed service contract that the rig validates independently. Network separation alone is not that validation.

Gate sequence:

1. **Channel gate:** authenticate the browser/device or Google/WhatsApp account; reject unknown senders and record provider event IDs. A sender allowlist is only an intake filter. Do not accept an email body as an authorization or a reply as high-impact approval.
2. **Request gate:** parse a versioned command or create a proposal. Match a registered workflow ID and exact JSON schema, canonicalize URLs/IDs, reject paths and unexpected fields, cap rate, concurrency, time, model budget, and output size. Avoid constructing shell commands from filtered strings; string sanitization is not an execution boundary.
3. **Harness gate:** issue a signed or otherwise authenticated capability envelope for the specific work item. The harness checks each tool call against it, including network destinations, file roots, recipients, and side-effect class. External content never changes this envelope.
4. **Rig gate:** use a dedicated low-privilege identity or constrained service for remote work, separate from manager/admin SSH. Accept only typed allowlisted operations and validate workflow, inputs, budget, and ownership again on the rig. A restricted SSH command (`ForceCommand`/`authorized_keys command=` with forwarding disabled) is one candidate transport; a dedicated broker over the private link is another. The rig must reject a forged or overbroad request even if it came from the Pi. [OpenSSH restricted command reference](https://man.openbsd.org/sshd.8).
5. **Approval and delivery gate:** privileged work requires an exact action preview and approval in an authenticated session with fresh authorization. Email/Drive output is restricted to named recipient and folder roles; model text cannot choose an arbitrary address or exfiltration destination. Keep append-only audit events for accepted, rejected, approved, executed, and delivered operations.

Run the Gmail/WhatsApp adapter as a separate Pi service/user with only mailbox access and a local intake socket; it should have no rig SSH key or direct access to manager endpoints. Run harness work under its own service identity. Keep the existing loopback dashboard/admin path separate from the session UI and remote channel endpoints. If this process separation is impractical in the first prototype, keep inbound execution disabled and allow only notification plus a queued proposal for local review.

The first security test suite should prove denials end to end: unauthorized account, spoofed display name, wrong command grammar, extra fields, malicious URL/path, prompt injection in mail/repo/web content, duplicate/replayed message, expired approval, disallowed tool or Drive recipient, direct manager/dashboard access from the channel service, and a forged Pi-to-rig work request. Also prove the accepted bounded workflow finishes and returns its own result. No remote general agent or build-work enablement until this boundary passes.

## Public repository and private deployment boundary

Publish the protocol, threat model, permission classes, default-deny rules, sample configs with fake identities, and security tests. The system must remain secure when an attacker reads every public line of code and documentation. Keep real OAuth refresh tokens and client credentials, SSH private keys, service-to-service authentication material, tailnet/account/device IDs, recipient allowlists, exact host routes, and backup recovery keys in a private deployment store. Do not commit an encrypted secret file alongside the key needed to decrypt it. `gitignore` is a backstop, not proof that a secret was never committed; run secret scanning on history and block new secret pushes. Rotate a credential found in a public commit even if that commit is later removed. [OWASP secrets guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html), [GitHub secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning).

The Pi should give the Google connector, session service, manager, and dashboard separate service identities and private credential access. A connector may read only its account token and local intake socket; the manager's rig key is unavailable to it. Make private credential directories owner-only and keep tokens owner-readable only. Use a platform secret store or an encrypted credential facility when selected; document how the decryption key is protected, rotated, backed up, and recovered. Encryption of a file is weak protection if the auto-starting service can read both ciphertext and its key from the same stolen medium. Disk encryption and encrypted backups address physical-media loss, but an unattended Pi reboot then needs a deliberate unlock design. Do not claim encryption at rest until that is deployed and tested. [Google OAuth storage guidance](https://developers.google.com/identity/protocols/oauth2/resources/best-practices), [OWASP cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).

Protect phone-to-Pi and Pi-to-rig traffic with authenticated encrypted transport; the private Ethernet alone is not encryption. Keep the existing admin path loopback-only and do not expose it through a session proxy. Decide whether reports may contain private data before publishing to Drive: a Drive link is a delivery mechanism, not an automatic declassification. For sensitive artifacts, either keep them local or encrypt them for a named recipient before upload, with the key outside Drive.

Deployment gate: inspect tracked files and Git history for secrets; verify effective file/parent-directory permissions, service users, ACLs, listening interfaces, forwarding, backup encryption, token renewal/revocation, and denial of cross-service credential access. Store the measured hostnames, account IDs, key paths, ACL values, and recovery instructions in a separate private operations runbook. The public repo should contain only the checklist and synthetic examples.
