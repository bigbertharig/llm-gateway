# Powerful gateway host and local child agents

Status: single-rig cloud-to-local path live and verified with the Qwen headless worker pool, 2026-11-18. The Pi remains the live controller. Multi-rig placement remains a design target.

## Target placement

A powerful GPU machine can be the main entrance to the system. It can run the gateway, an agent harness, and the rig hardware layer for its own GPUs. The same gateway can coordinate a weaker remote rig. Each rig retains its own GPU leases, plan, health checks, and runtime enforcement. The controller chooses a rig and a placement from each rig's report; model splits stay within one rig.

The current gateway manages one rig. Reaching this target requires a rig list, per-rig observation and model-port connections, placement across rigs, and the rig hardware interface on the powerful host. The Pi may remain a storage and network host even after controller duties move.

## Coding-session entry point

The *main* chat is the controlling conversation, not a required GPU placement or model size. A cloud Codex main chat has no local KV context; its local chats are child agents. A local model can also be the main chat and delegate to other local chats. The current Qwen headless recipe reserves GPU0 for shared weights and service state, but does not place a controlling chat there. That placement is a property of the tested recipe, not a general rule for all rigs.

### Chat and service terms

| Term | Meaning | Owner |
| --- | --- | --- |
| Main chat | The durable conversation whose user request directs work and receives agent results. It may use a cloud or local model and may be moved to another model while retaining its saved history. | Gateway session identity; harness conversation state |
| Agent chat | An independently bounded, delegated conversation with its own context, task, tools, and receipt. It returns work to a main chat; it need not use a smaller model. | Harness lifecycle; Gateway route and admission |
| Shared model service | Loaded weights and runtime resources that can serve multiple chats. A headless service can exist with no main chat on the rig. | Orchestration runtime and hardware state |
| Service parent reservation | The rig's reservation for shared weights and parent-side memory. The legacy key `reservations.main` names this service record even when no controlling conversation exists. | Orchestration |

Gateway decides which conversation is main and which requests are delegated. It sends a requested model or capability, context reservation, and service recipe to orchestration; orchestration admits and places the physical chat without deciding its conversational role. The names `gpu0-main-q4` and `main` in the current runtime are legacy service handles, not a requirement that the controlling chat use GPU0. Model-library load recipes describe *where and how* weights and contexts fit; a candidate in `subagent_catalog` describes which of those contexts is offered for delegation. No model or GPU is inherently a main or agent chat. A local main chat and its agents can share one model service when a tested recipe supports it, or use separate services. A cloud main chat can use the headless worker pool.

## Tool catalog handoff

The harness owns both dashboard MCP servers and the full `tools/tool_registry.json` inventory. It generates `tools/dashboard_tool_catalog.json` from the dashboard subset with `python3 tools/export_dashboard_tool_catalog.py sync`. The gateway imports that list with `python tools/sync_harness_tools.py --source ../llm-harness/tools/dashboard_tool_catalog.json what-new`, `sync`, or `check`. The dashboard bridge and local chat runner read only the gateway-imported `src/llm_gateway/dashboard/tool_catalog.json` for enabled tools and exact permission requests. Publish new tools as `disabled`, review their behavior and boundary policy, then switch to `automatic` and sync. A new MCP server also needs a gateway launch configuration. `list_local_agents` is a tool that reports agent roles and model offers from the manager, not the tool catalog. See the adjacent cross repo communication contract for the ownership and runtime flow.

## Network boundary

The Codex model connection uses the internet. The `local_agents` MCP adapter is started by the Codex app-server as a local stdio process on the gateway host. It calls the gateway's loopback API; the gateway reaches the rig over the private SSH connection. Tool arguments and results are visible to the cloud model as part of the session. The Codex command sandbox requests `networkAccess: false`, but MCP processes run on the host side, so that setting alone does not enforce MCP egress. Each additional MCP tool needs its own network policy and explicit allowlist. Host firewall or process isolation is needed for a hard outbound network boundary.
