# llm-gateway

OpenAI-compatible endpoint for Big Bertha rig models, running on the Pi: the one front door for
the rig. Clients (Roo in VS Code) pick a model from `/v1/models`. The first request for a model
makes the rig load it (`rig start remote <id>` over ssh) and holds the request until it's ready.
Later requests go straight through. While a load runs, `/v1/rig/status` lists it under
`gateway_loading` with its elapsed time.

Cloud models are not routed here. Roo uses its native OpenRouter provider for those.

```text
client on the Pi -> Pi 127.0.0.1:8080 llm-gateway (pi-gateway.service)
                       |  ssh 10.0.0.3 rig status --json / rig start remote <id>
                       `-> Pi 127.0.0.1:<port> --pi-rig-tunnel.service--> rig 127.0.0.1:<port> llama-server
```

From another machine, ssh to the Pi and work there, or forward the Pi's 8080
(`ssh -L 8080:127.0.0.1:8080 pi`). The rig's runtimes stay loopback-only; only the Pi talks to them.

## Models

The model registry (benchmarking repo, `model_registry.json`) is the one source of truth for how a
model loads. This repo owns only the offer: `OFFER` in `tools/generate_profiles.py` names each
published profile, its model, the registry profile to use (usually `interactive`), its GPU shape
(`gpus_needed`, optional `tensor_split`) and a description. The script resolves just those models
through the registry and writes `remote_profiles.json` (generated, committed, do not edit).

```bash
tools/generate_profiles.py            # after an OFFER edit or a registry change (run on the Pi)
tools/generate_profiles.py --check    # exit 1 if an offer is invalid or the file is stale
```

The gateway publishes each profile as `gpu-rig/<id>` with its `context_length`, and re-reads the
file when it changes, so no restart is needed. The rig mode selector (`rig start remote <id>`)
reads the deployed copy, `~/llm-gateway/remote_profiles.json`, and decides placement (which GPUs,
which port). Offers may use `active` or `candidate` registry models.

## API

| Route | Notes |
|---|---|
| `GET /v1/models` | one entry per remote profile |
| `POST /v1/chat/completions`, `POST /v1/completions` | streaming and non-streaming. Body forwarded unchanged |
| `POST /tokenize`, `POST /detokenize` | llama-server tokenizer, routed by `model`, e.g. `{"model": "gpu-rig/chat-27b", "content": "..."}`. Exact counts for compaction |
| `GET /v1/rig/status` | `rig status --json`, plus `gateway_loading`: loads in progress with `since` and `elapsed_s` (the rig reports a profile only once it is ready) |
| `GET /health` | liveness |
| `/v1/manager/...` | rig manager: `status`, `leases` (acquire, renew, release), `claims`, `profiles/<id>/load\|unload`, `reconcile`. Process and rules: [docs/MANAGER.md](docs/MANAGER.md). CLI: `tools/rigctl.py` |

Errors use the OpenAI shape `{"error": {"message", "type", "code"}}`:

| Situation | Status |
|---|---|
| unknown model | 404 (message lists published ids) |
| prompt larger than the profile's context | 400 `context_length_exceeded`, OpenAI wording, so harnesses compact and retry |
| rig busy in another mode (orchestration/bench) | 503 `rig busy: ...` |
| not enough free GPUs for the profile | 503 with the loaded profiles |
| load failed | 502 with the rig error |
| rig unreachable (ssh exit 255) | 502 `rig unreachable over ssh: ...` |
| load exceeded `START_TIMEOUT_SECONDS` | 504; the load keeps running on the rig |
| API keys configured, key missing or wrong | 401 `invalid_api_key` |

Concurrent cold requests for one profile share a single load.

## Configuration (environment)

| Variable | Default | Notes |
|---|---|---|
| `RIG_COMMAND` | `rig` | Pi service: multiplexed `ssh ... 10.0.0.3 /usr/local/bin/rig` (see `deploy/pi-gateway.service`). ssh exit 255 maps to 502 "rig unreachable" |
| `PROFILES_PATH` | `remote_profiles.json` in this repo | generated by `tools/generate_profiles.py` |
| `UPSTREAM_HOST` | `127.0.0.1` | host serving profile ports (on the Pi: its end of `pi-rig-tunnel.service`) |
| `MODEL_PREFIX` | `gpu-rig` | |
| `GATEWAY_BIND` / `GATEWAY_PORT` | `127.0.0.1` / `8080` | a non-loopback bind is refused unless API keys are configured |
| `GATEWAY_API_KEYS_FILE` | `/etc/llm-gateway/api_keys` | one bearer key per line (`#` comments). Missing file = auth off. With keys, every route but `/health` needs `Authorization: Bearer <key>` (401 `invalid_api_key` otherwise) |
| `MANAGER_SHARED_PATH` | unset (manager off) | Pi service: `/media/bryan/shared`. With it, cold loads take a lease and go to the rig as one detached job |
| `MANAGER_LEASES_LIB` | `<shared>/agents/gpu_leases.py` | the lease store module (orchestration repo) |
| `START_TIMEOUT_SECONDS` | `900` | |
| `REQUEST_TIMEOUT_SECONDS` | `900` | |

## Run, test, deploy

FastAPI + uvicorn + httpx (Python >= 3.11), in a per-host `.venv`.

```bash
python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'
.venv/bin/python -m pytest -q                    # fake rig + fake llama-server
.venv/bin/python -m llm_gateway                  # run locally (env vars above)
deploy/deploy_pi.sh                              # on the Pi: check profiles, copy repo to the rig, restart Pi services
```

On the Pi it runs as `pi-gateway.service`, with `pi-rig-tunnel.service` forwarding the rig's
remote ports 11434-11441 to Pi loopback (both enabled at boot; nothing loads until asked). The rig
gets a copy of this repo only so `rig start remote` can read `remote_profiles.json`.

A `rig start` is never killed by the gateway: over ssh that could stop a load half-way and free
the rig's model-load lock. Past `START_TIMEOUT_SECONDS` the request gets a 504 and the load
continues; the next request finds it ready.

## Checking models

`tools/model_check.py` exercises each profile through the gateway the way a harness would:
load time, advertised vs served context, thinking leak, streaming, tool calling, `/tokenize`,
prompt tok/s at growing prompt sizes, and the overflow error. Reports go to `results/` (gitignored).

```bash
# on the Pi (--exclusive runs rig over ssh):
.venv/bin/python tools/model_check.py --profiles coder-7b chat-27b
.venv/bin/python tools/model_check.py --profiles coder-30b devstral-24b gpt-oss-20b --exclusive
```

`--exclusive` unloads every other profile before each one. Needed for the 3090-only candidates,
since there's no auto-evict.

## Repo layout

- `src/llm_gateway/`: the gateway
- `tools/`: operator tools (profile generator, model check)
- `remote_profiles.json`: generated offer, read by the gateway and `rig`
- `deploy/`: rig systemd unit + deploy script
- `docs/harness/`: agent-harness research and backlog (parked). Upstream clones live alongside in `~/`.
